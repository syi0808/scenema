# Scenema 랜딩·데모 통합 개편 계획

## 1. 목표

Scenema의 랜딩 페이지 자체를 실제 데모 대상으로 사용한다. 방문자는 별도의 가상 제품 화면으로 이동하지 않고, 랜딩에 있는 예제 선택기, 입력 필드, 버튼, URL, 코드 패널을 Scenema가 직접 조작하는 과정을 본다.

개편 후 페이지는 다음 질문에 순서대로 답해야 한다.

1. Scenema가 무엇인가?
2. 실제 화면에서 무엇을 수행할 수 있는가?
3. 여러 동작을 개별적으로 체험할 수 있는가?
4. 방금 본 동작을 어떤 코드로 정의하는가?
5. 어디에서 설치하거나 자세히 볼 수 있는가?

## 2. 확정된 결정

- 랜딩 페이지와 메인 데모를 하나의 인터페이스로 결합한다.
- 현재 `Northstar` 프로젝트 생성 데모와 제품 셸은 제거한다.
- 랜딩에서 성공적으로 수행되는 기능 예제만 제공한다.
- 복원, 오류 처리, 잘못된 타깃 등 실패 사례는 랜딩 예제에서 다루지 않는다.
- 사용 사례와 사용 기업, 다운로드 수치 같은 신뢰 정보 섹션은 이번 범위에서 제외한다.
- 컬러 팔레트와 디자인 토큰 변경은 별도의 디자인 작업으로 남긴다.

## 3. 페이지 구조

### 3.1 헤더

- Scenema 브랜드와 홈 링크
- `Examples`, `Code`, `GitHub` 탐색 링크
- 어느 스크롤 위치에서도 데모를 다시 시작할 수 있는 `Show demo` 버튼
- 모바일에서는 브랜드와 `Show demo`만 유지하고 나머지는 메뉴 또는 본문 링크로 축소

### 3.2 히어로

- 제품 범주를 바로 이해할 수 있는 제목
- 클릭, 입력, 경로 이동을 실제 인터페이스에서 수행한다는 한 문장 설명
- 기본 CTA `Show demo`
- 보조 CTA `Get started`
- 메인 투어의 첫 안내가 히어로를 대상으로 열리며, 별도 데모 영역으로 먼저 스크롤하지 않음

### 3.3 기능 요약 스트립

- `Real clicks`, `Real typing`, `Route-aware`, `User-paced`처럼 데모에서 확인할 핵심 특성만 짧게 표시
- 사회적 증거나 성과 수치가 아니라 제품 동작의 탐색 보조 장치로 사용
- 메인 투어의 진행 단계로 사용하지 않아 데모 흐름을 늘리지 않음

### 3.4 Examples

방문자가 각 기능을 독립적으로 실행할 수 있는 실제 플레이그라운드다. 메인 투어 역시 같은 요소를 대상으로 동작한다.

| 예제      | 방문자 단독 실행                           | 메인 투어에서의 동작                                          |
| --------- | ------------------------------------------ | ------------------------------------------------------------- |
| Highlight | 버튼을 누르면 지정 요소를 강조             | 지정 요소를 가리키며 Scenema의 타깃 지정 방식을 설명          |
| Click     | 버튼과 카운터를 제공                       | Scenema가 버튼을 클릭하고 카운터가 증가                       |
| Type      | 레이블이 있는 입력 필드와 초기화 버튼 제공 | Scenema가 입력 필드에 `Launch workspace`를 입력               |
| Navigate  | 다음 예제로 이동하는 버튼과 현재 경로 표시 | Scenema가 버튼을 클릭해 경로를 변경하고 같은 투어를 계속 진행 |

예제 선택기는 탭 인터페이스로 제공하며 URL과 선택 상태를 연결한다.

- `/examples/highlight`
- `/examples/click`
- `/examples/type`
- `/examples/navigation`

홈에서 직접 예제를 선택할 때는 `history.pushState`로 경로를 반영한다. 브라우저 뒤로 가기와 앞으로 가기에서도 선택된 예제가 동기화되어야 한다.

### 3.5 Code

- Examples와 동일한 네 개의 탭을 제공
- 선택된 예제가 바뀌면 해당 코드도 함께 변경
- 코드의 타깃 선택자와 화면 요소의 식별자가 실제로 일치해야 함
- 메인 투어의 마지막 단계에서 현재 실행된 시나리오 코드를 강조
- 설치 명령과 문서 링크를 코드 아래에 배치

### 3.6 최종 CTA

- 데모에서 확인한 핵심 결과를 한 문장으로 요약
- `Get started`와 `View on GitHub` 두 가지 다음 행동만 제공
- 새로운 기능 설명이나 반복 데모는 추가하지 않음

## 4. 메인 통합 데모 시나리오

메인 데모는 30초 안에 완료되는 다섯 단계로 제한한다.

### Step 1. 랜딩 자체가 데모임을 안내

- 시작 위치: 히어로
- 대상: 히어로의 제품 설명 또는 `Show demo` 주변
- 행동: 없음
- 메시지: 별도 샌드박스가 아니라 현재 페이지를 직접 조작한다는 점을 설명

### Step 2. 실제 클릭

- 대상: Click 예제의 실행 버튼
- 진입 전 Examples 섹션과 Click 탭을 화면에 표시
- 행동: 사용자가 `Next`를 선택하면 Scenema가 버튼을 클릭
- 완료 조건: 카운터 값이 증가

### Step 3. 실제 입력

- 대상: Type 예제의 입력 필드
- 행동: `Launch workspace` 입력
- 완료 조건: 입력 필드의 값이 예상 문자열과 일치

### Step 4. 경로 이동

- 대상: Navigate 예제의 이동 버튼
- 행동: 버튼 클릭 후 `/examples/navigation`으로 이동
- 완료 조건: 주소와 선택된 예제가 모두 Navigation 상태를 표시
- 메시지: 경로가 바뀌어도 같은 시나리오가 이어지고 있음을 설명

### Step 5. 코드 연결

- 대상: Navigation 코드 패널
- 행동: 없음
- 메시지: 방금 실행한 타깃, 행동, 전환이 동일한 시나리오 정의에 들어 있음을 설명
- 완료 후: 포커스를 데모 시작 버튼으로 복귀하고 완료 상태를 짧게 표시

## 5. 상태와 내비게이션

### 5.1 페이지 상태

랜딩에서 관리할 최소 상태는 다음과 같다.

- 선택된 예제
- Click 예제 카운터
- Type 예제 입력값
- 메인 투어 실행 여부
- 메인 투어 완료 여부

예제 상태는 데모를 다시 실행할 때 초기화한다. 랜딩 데모는 항상 같은 결과를 재현할 수 있어야 한다.

### 5.2 경로 처리

- `/`은 Highlight 예제를 기본 선택
- `/examples/:example`은 동일한 랜딩 셸을 렌더링하고 해당 예제를 선택
- 알 수 없는 예제 경로는 홈 기본 상태로 정규화
- 직접 URL 접근, `popstate`, 메인 투어의 경로 전환이 하나의 경로 해석 함수를 사용
- 배포 시 `BASE_URL`이 있는 환경에서도 동일하게 동작

### 5.3 데모 재시작

- 헤더와 히어로의 `Show demo`는 동일한 시작 함수를 사용
- 실행 중 다시 시작하면 현재 세션을 종료하고 예제 상태와 경로를 초기화한 뒤 처음부터 시작
- 완료 후에는 `Run again`으로 레이블을 변경할 수 있지만 버튼 위치는 유지

## 6. 컴포넌트 변경 계획

### 제거

- `apps/site/src/lib/DemoStage.svelte`
- 제품 셸, 프로젝트 목록, 생성 폼, 상세 단계 레일과 관련된 스타일
- `/try/projects` 기반 랜딩 데모 시나리오

### 추가

- `apps/site/src/lib/Hero.svelte`: 히어로 콘텐츠와 데모 시작점
- `apps/site/src/lib/Examples.svelte`: 탭, 플레이그라운드, 예제 상태
- `apps/site/src/lib/CodeShowcase.svelte`: 선택된 예제와 연결된 코드 탭
- `apps/site/src/lib/LandingDemo.svelte`: 메인 시나리오 정의와 시작·중지·초기화 제어

### 수정

- `apps/site/src/App.svelte`: 새로운 페이지 순서와 공유 상태 조립
- `apps/site/src/lib/Header.svelte`: Examples, Code, 데모 시작점으로 탐색 구조 변경
- `apps/site/src/styles.css`: 제거된 제품 셸 스타일 정리 및 새 섹션 레이아웃 추가
- `README.md`: `/try/projects` 설명을 랜딩 통합 예제로 교체
- `tests/site.test.ts`: 기존 프로젝트 생성 테스트를 랜딩 통합 시나리오 테스트로 교체

컴포넌트 사이에는 DOM 요소 자체가 아니라 선택된 예제, 시작 함수, 초기화 함수만 전달한다. 실제 타깃은 안정적인 `id` 또는 `data-demo-target` 속성으로 찾는다.

## 7. 반응형 동작

- 메인 투어는 데스크톱과 모바일에서 같은 논리적 다섯 단계를 사용
- 각 단계 시작 전에 대상 요소를 화면 안으로 스크롤
- Examples 탭은 모바일에서 가로 스크롤 또는 2열 배치
- 플레이그라운드는 모바일에서 한 열로 표시하고 모든 조작 요소를 화면 너비 안에 유지
- 코드 패널은 가로 스크롤을 허용하되 페이지 전체의 가로 스크롤은 발생시키지 않음
- 팝오버가 입력 필드나 실행 버튼을 가리지 않도록 모바일 배치를 별도로 지정
- 데모를 시작하지 않은 모바일 방문자도 모든 예제를 직접 실행할 수 있어야 함

## 8. 접근성과 사용자 제어

- 모든 탭은 키보드로 전환 가능하고 선택 상태를 프로그램적으로 전달
- 예제 결과는 `aria-live` 영역으로 알림
- Type 예제는 명시적인 레이블을 제공
- 메인 투어는 언제든 닫거나 다시 시작할 수 있음
- 투어 종료 후 시작 버튼으로 포커스 복귀
- `prefers-reduced-motion`에서는 커서 이동과 자동 스크롤 애니메이션을 줄이되 클릭과 입력 결과는 동일하게 유지
- URL 변경은 문맥 변화가 있었음을 보조 기술에 알림

## 9. 테스트 계획

### 통합 시나리오

1. 홈에서 메인 데모를 시작한다.
2. Click 단계에서 버튼이 실제로 클릭되고 카운터가 증가하는지 확인한다.
3. Type 단계에서 예상 문자열이 입력되는지 확인한다.
4. Navigate 단계에서 URL과 활성 탭이 함께 변경되는지 확인한다.
5. Code 단계에 도달하고 투어가 정상 완료되는지 확인한다.
6. 다시 실행했을 때 카운터, 입력값, 경로가 초기화되는지 확인한다.

### 독립 예제

- 네 개 예제가 메인 투어 없이 각각 실행되는지 확인
- 예제 탭과 브라우저 뒤로 가기·앞으로 가기가 동기화되는지 확인
- 직접 예제 URL로 접근했을 때 올바른 탭이 선택되는지 확인

### 품질 확인

- 키보드만으로 Examples와 CTA를 사용할 수 있는지 확인
- reduced motion 환경에서 시나리오가 완료되는지 확인
- 390px 모바일과 1440px 데스크톱에서 팝오버가 타깃을 가리지 않는지 확인
- 사이트 테스트, 타입 검사, 린트, 프로덕션 빌드를 통과하는지 확인

## 10. 구현 단계

### Phase 1. 랜딩 구조 전환

- 새 페이지 순서와 컴포넌트 경계를 구현
- 기존 `DemoStage`와 `/try/projects` UI 제거
- 헤더와 히어로의 데모 시작점을 통합

### Phase 2. 독립 Examples 구현

- 네 개의 예제와 공유 선택 상태 구현
- 예제 경로와 브라우저 내비게이션 연결
- 각 예제를 투어 없이 직접 사용할 수 있도록 검증

### Phase 3. 메인 시나리오 연결

- 다섯 단계 랜딩 시나리오 정의
- 클릭, 입력, 경로 변경, 코드 강조 연결
- 재시작과 초기화 동작 구현

### Phase 4. Code와 CTA 완성

- 예제와 코드 탭 동기화
- 설치 및 문서 진입점 정리
- 완료 상태와 최종 CTA 연결

### Phase 5. 반응형·접근성·테스트

- 모바일 팝오버와 섹션 배치 조정
- 키보드, 포커스, live region, reduced motion 검증
- 기존 사이트 테스트 교체 및 전체 검증 실행

## 11. 완료 기준

- 별도의 가상 제품 셸 없이 랜딩 자체에서 메인 데모가 완료된다.
- 메인 데모가 실제 클릭, 실제 입력, URL 변경을 모두 보여준다.
- 네 개의 예제를 메인 투어 없이도 독립적으로 실행할 수 있다.
- 예제 선택, URL, 코드 패널이 항상 같은 기능을 가리킨다.
- 데모를 반복 실행해도 동일한 초기 상태와 결과를 얻는다.
- 데스크톱과 모바일에서 동일한 시나리오가 중단 없이 완료된다.
- 복원·오류 처리 실패 사례, 사용 사례, 신뢰 정보는 랜딩에 추가되지 않는다.
- 관련 테스트, 타입 검사, 린트, 빌드가 통과한다.

## 12. 범위 밖 작업

- 컬러 팔레트와 디자인 토큰 재정의
- 마스코트 또는 신규 브랜드 일러스트 제작
- 고객 로고, 사용량, GitHub 통계 등 사회적 증거
- 산업별 사용 사례 콘텐츠
- 복원, 오류 처리, 실패 경로를 보여주는 공개 예제
- 문서 사이트의 전체 정보 구조 개편
